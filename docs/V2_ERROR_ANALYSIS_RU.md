# Экокинеу: диагностика V2 и следующий эксперимент

**Массовые пропуски не объясняются ошибкой проверенного preprocessing, class mapping или экспорта.** На выбранных контролях PyTorch и OpenVINO дают одинаковые рамки. Кандидат слаб в переносе на отдельные отходы и часто реагирует на похожие текстуры. V2 остаётся отклонённой, tiled inference не подключён. Нового долгого прогона не запускалось, пользовательские фото в этом анализе не использовались.

## Проверенный путь данных и inference

- Все634 файла строгой бинарной V2 проверены по SHA256. Проверены2379 bbox: COCO category1 → YOLO class0 → `trash`; исходные source category ID входят только в12 разрешённых категорий. Context-only не превращался в пустую бинарную метку. Обратное преобразование COCO/YOLO отличается максимум на0.00000032 px.
- Сравнён реальный вход адаптера с установленным официальным `Ultralytics LetterBox(auto=False,640,stride32)`: RGB,float32,NCHW,/255,поля114. В9 случаях входной тензор совпал побитно. Есть квадратные640 кадры, реальные1280×720 и искусственный701×433 resize публичного кадра только для проверки геометрии.
- PyTorch `.pt` и OpenVINO `.xml/.bin` сравнены на одном и том же тензоре: raw shape1×5×8400, один класс без отдельного objectness. Максимальная raw-погрешность координат0.003693 px, score0.000001699. Все значения конечны.
- После официального PyTorch NMS и адаптера совпали все33 рамки на9 контролях; максимальное расхождение bbox0.000245 px. Порог0.20, class NMS IoU0.45,max100. Контроли с непустым выходом специально взяты из уже просмотренных development-результатов; это проверка реализации, не оценка качества выборки.
- NMS выполняется до clipping; RGB/letterbox, NaN, исключённый класс и этот порядок проверены5 регрессионными тестами. Найдено16 пар исходных GT-bbox с IoU>0.45 в13 изображениях на2379 аннотаций. Это повод проверять гранулярность/перекрытия меток, но не доказательство, что NMS вызывает все пропуски.

Проверка охватывает указанные режимы и данные, а не доказывает отсутствие любых ошибок во всех будущих размерах/форматах. Производственные файлы detector/registry в ходе анализа не менялись.

## Масштаб и тип ошибок

При фиксированном0.20 и IoU0.5, test-development:

| Площадь bbox | Совпало / целей | Recall |
|---|---:|---:|
| small,area<32² px |3/58|5.17%|
| medium,32²≤area<96² |105/414|25.36%|
| large,area≥96² |47/118|39.83%|

Это стандартные границы по площади, а не минимум ширины/высоты. В V2 исходник640×640, поэтому здесь нет уменьшения полного кадра при входе640. Низкий recall остаётся даже для крупных объектов: увеличение разрешения само по себе недостаточно.

Из435 пропущенных целей271 имеют совпадающий по IoU≥0.5 кандидат в сохранённом выходе при минимальном score0.01, но ниже рабочего0.20;21 имеют перекрытие с рамкой≥0.1 при недостаточном IoU, остальные143 не перекрыты предсказанием при0.20. Это диагностическая группировка выходов после NMS, а не строгая причинная атрибуция сырых proposals. Снижение порога не решает качество: на validation при0.10 TP12/FP34, precision26.1%; при0.20 TP9/FP13, precision40.9%.

Сохраняются дисбаланс и разные сценарии. В строгом train629 из1743 объектов — textile; в val textile нет. В test355 из590 объектов — поддоны. Модель пропускает упаковку/пластик и объединяет соседние предметы в большие рамки. Возможные причины — недостаток нужных видов отходов, смешанная гранулярность аннотаций, доменный сдвиг и замороженный backbone. Их вклад по отдельности пока не измерен, это гипотезы для следующего контролируемого опыта.

## Tiled inference: отдельный отрицательный результат

До inference выбраны первые4 публичных UAVVaste validation кадра по SHA256, все1280×720; эти данные уже development, не новый holdout. Ни пользовательские фото, ни их предсказания для выбора параметров не использовались.

Фиксированы640×640 окна, шаг480, покрытие правого/нижнего края, глобальный class NMS0.45 и confidence0.20. На каждом изображении6 окон; у границ фактическое перекрытие может быть больше160px. Два синтетических geometry-теста проверили смещение bbox, удаление дублей и покрытие нижнего/правого края; их изображения не сохраняются как реальные наблюдения.

Полный кадр:0 рамок,0/8 совпадений. Tiled:46 рамок,0/8 совпадений по исходной разметке. Два проблемных кадра просмотрены: модель выделяет сетку мощения, грунт и бордюр, пропуская размеченные бутылки/упаковку. Это указывает на ложную связь с текстурой; полнота исходных меток всё равно не гарантируется.

Однократные замеры этих4 кадров,2 CPUthreads: среднее full0.221с, tiled1.349с (~6.1×). Это маленький диагностический замер, не обещание скорости потока/дрона. Больших проверенных чистых кадров для оценки tiled-FPR здесь нет. Включать режим в пилот по этому результату нельзя.

## Разморозка backbone: измерение ресурсов

В отдельных процессах выполнено по4 шага в памяти на двух фиксированных публичных train-фото, batch2,640px,AdamW,CPU2threads. Первый шаг исключён, приведена медиана3 следующих. Все изменённые веса отброшены; original best.pt и рабочая registry после проверки имеют прежние SHA256. Это microbenchmark, не новый обучающий run и не метрика точности.

| Режим | Trainable parameters | Медиана шага | Peak RSS процесса |
|---|---:|---:|---:|
| freeze10 |1,474,275|1.190с|946.2MiB|
| freeze0,DFL остаётся фиксированным |2,590,019|2.361с|1169.8MiB|

Полная разморозка здесь примерно1.98× дороже по шагу, +224MiB peak RSS. В замер не входят augmentation,чтение данных,validation или export. Формула нижней оценки compute:ceil(Ntrain/2)×2.361с на эпоху; для449 кадров это531с без остальных затрат. Срок нового прогона неизвестен до размера/состава новых данных и первой реальной эпохи. При малом свободном RAM batch1 надо отдельно измерить; нельзя обещать, что RAM/время уменьшатся ровно вдвое.

## Конкретный следующий план под новые данные — пока не запущен

1. Принять версионный street/water набор с лицензиями, file/pixel hashes, группами места/сессии/источника, исключить user-фото из train. Новые места зафиксировать в holdout до просмотра/подбора; неизвестная география не становится доказанной независимостью только из-за другого имени файла. Старые test-площадки только regression/development.
2. Определить один объектный target: упаковка, бутылки, пакеты и другие видимые отходы. Крупная рамка скопления не должна подменять множество отдельных объектов. Спорные scene/pile кадры сохранить отдельно; при исключении их меток нельзя оставлять такой кадр пустым background. Пересмотреть вложенные/дублированные bbox и сохранность сегментаций. Не переименовывать грунт/камни/крыши в pollution.
3. Балансировать источники и типы кадров, добавить проверенный фон: гравий, плитка/решётки, бордюры, грунт, растительность, вода/блики. На просмотренных tiled-кадрах обнаружена особенно важная путаница с сеткой покрытия. Не давать textile/поддонам подавлять street/water. Точные доли и объём replay старого train зафиксировать после инвентаризации новых данных, не за счёт test.
4. Базовый следующий кандидат:YOLO11n,640px,batch2,CPU2threads,workers0,cache=false,freeze0,AdamW,lr0≈3e-4,warmup1epoch,max20epochs,patience5,жёсткий бюджет4ч с остановкой на границе эпохи,best/last каждую эпоху. Стартовый V2 checkpoint разрешён только как init обучения, не как готовая модель; COCO-init остаётся контрольным вариантом, если validation показывает отрицательный перенос. Рецепт/инициализацию зафиксировать до просмотра нового holdout.
5. Перед длительным запуском измерить один новый epoch и available RAM. Если запас мал относительно измеренных~1.17GiB процесса плюс приложения — сначала измерить batch1/согласовать временную паузу тяжёлого анализа, не убивать чужие процессы. Пилот/БД и оригиналы сохранять. Конкретный ETA дать по фактической эпохе, не по microbenchmark.
6. Отбирать checkpoint/порог только на validation с отдельно показанными object recall,precision,negative-image alarm rate,сценовыми ошибками и source/category breakdown. Прежние минимумы0.50/0.25/≤0.10 — только нижний фильтр, не production-приёмка. Tiled рассматривать повторно лишь после исправления features/данных, с заранее фиксированными окнами, отдельными большими negatives и latency; не использовать его как способ нарисовать больше рамок.
7. После фиксации кандидата — отдельная оценка нового holdout, локальный просмотр ошибок, версия/откат; activation только после принятия. Пользовательские фото допускаются лишь как отдельная ненастроенная диагностика, не train и не источник порога.
