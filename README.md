# Агро Кинеу / Экокинеу

Локальное приложение для анализа отдельных JPEG/PNG. Основной интерфейс: **http://127.0.0.1:8010/**. Подключение дрона, видеопоток и управление полётом в этом пилоте не реализованы.

## Направления

| Вкладка | Что анализирует | Исходная модель |
| --- | --- | --- |
| Сорняки | Только `weed` | Сохранённый DINOv2 reference baseline |
| Мусор | Только `trash` | Детектор в карантине; принятой модели сейчас нет |
| Дым и огонь | Раздельные классы `fire`, `smoke` | Сохранённый экспериментальный fire/smoke baseline |
| Общий анализ | Эти три направления последовательно, на одном фото | Отдельной четвёртой модели нет |

Каждая вкладка открывает собственную историю анализа, версии, настройки, датасеты и обучение. Ошибка или недоступность класса отображается отдельно от успешного анализа без находок. Исторический режим `environment` остаётся совместимым со старыми записями и охватывает мусор, огонь и дым.

Общий анализ допускает частичный результат: например, ошибка сорняков не превращает выполненный анализ огня в ошибку всего снимка. В результат записываются фактически выполненные классы и ошибки. Фото и рамки можно просматривать и проверять вручную; GPS обозначает положение камеры, а не точные координаты объекта.

## Установка и локальный запуск

Нужны Python с совместимыми PyTorch/OpenVINO, системные `mariadbd` и `mariadb-install-db`. Для необязательных C++-сборок нужен `g++`. Зависимости Python перечислены в `requirements.txt`; текущая проверенная среда использовала Python 3.14.8 и OpenVINO 2026.4.1. Проект не содержит воспроизводимого lock-файла всех транзитивных зависимостей.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
bash scripts/start_pilot.sh
```

Скрипт поднимает отдельную проектную MariaDB через приватный Unix socket, без TCP, затем запускает HTTP-сервер только на `127.0.0.1`. Адрес по умолчанию — http://127.0.0.1:8010/; другой порт задаётся переменной `ECOKINEU_PORT`. Параллельный обработчик той же очереди не допускается.

Код не содержит исходных изображений, весов и приватных настроек БД. На новой машине нужно отдельно восстановить разрешённые локальные данные, веса и offline-кэш DINOv2 из сохранённой копии. Реестр моделей `artifacts/ecokineu-models.json` содержит пути и контрольные суммы, но не сами веса. Отсутствие файла или несовпадение hash — явная ошибка, а не повод скачать случайную замену.

Для ручного запуска уже настроенного проекта:

```bash
.venv/bin/python scripts/local_db.py
.venv/bin/python web_pilot.py --port 8010
```

Остановка HTTP-сервера — `Ctrl+C`; состояние снимков и прогоны сохраняются. При перезапуске незавершённый анализ становится ошибкой с возможностью повторить его. Незавершённое обучение не перезапускается автоматически. Живой процесс обучения, оставшийся после остановки сервера, распознаётся по PID и команде; до его завершения новые тяжёлые задания ждут.

## Данные и обучение

Исходные `data/`, `datasets/`, сохранённые веса и старые прогоны сохраняются. Новые файлы разделены:

```text
outputs/directions/
  weeds/       config.json, models.json, dataset/, runs/<id>/
  trash/       config.json, models.json, dataset/, runs/<id>/
  fire_smoke/  config.json, models.json, dataset/, runs/<id>/
```

В своей вкладке можно загрузить фото и YOLO-разметку, выбрать train или validation и просмотреть сохранённые фото/метки. Формат строки: `class cx cy width height`, координаты нормированы в диапазон 0–1. Классы: сорняки — `0 weed`; мусор — `0 trash`; свой набор дыма/огня — `0 fire`, `1 smoke`. Пустая явно переданная разметка означает проверенный negative; отсутствующий label-файл negative не считается. Одинаковый файл нельзя добавить в train и validation. Разные кадры одного поля/события нужно группировать вручную: автоматическая географическая независимость не обеспечивается.

Пока своего полного train/val нет, для мусора доступен замороженный `litter-v3-land`, для дыма — `smoke-pyrosdis-v1`. Последний содержит **только дым**: он не обучает огонь. Для сорняков эталонные фото `data/Сорняки` не заменяют bbox-разметку; обучение нового YOLO-кандидата становится доступным после добавления собственного train/val. Прежний DINOv2 baseline при этом сохраняется.

Обучение запускается кнопкой во вкладке. Настройки и веса каждого нового прогона изолированы. Ограничения очереди: один процесс, CPU, два потока, batch 1, 1–3 эпохи; временной бюджет 15 минут с внешним пределом 16 минут и остановкой процесса при RSS свыше 3 GiB. Анализ фото и собственное обучение сериализованы; учитывается также lock прежних training-скриптов. Есть отмена ожидающего и работающего задания, реальный журнал процесса и validation-метрики по классам. Проценты прогресса не имитируются.

Ultralytics пишет label cache даже при `cache=False`, поэтому тренер создаёт внутри прогона отдельное представление train/val: ссылки на изображения и копии labels. Cache и выходные веса не попадают в исходный датасет. Перед запуском проверяется замороженный snapshot. По окончании кандидат экспортируется в OpenVINO **без активации**.

## Версии и допуск модели

Кнопка выбора/отката работает только с принятыми версиями направления. `models.json` сохраняет историю выбора и ссылки на неизменяемые веса; первоначальный реестр не переписывается. Выбор smoke-only версии сохраняет прежний маршрут `fire`.

Новая обученная версия остаётся кандидатом. Кнопка «Проверить допуск версии» не заменяет независимую оценку: она проверяет подготовленные в папке прогона `manual-review.json`, `development-evaluation.json`, `native-parity.json`, hash весов и совместимость с реальным OpenVINO-адаптером. Автоматической генерации независимого holdout и экспертного решения в интерфейсе нет.

Контракт допуска для отдельного проверяющего процесса:

- `manual-review.json`: `verdict: approved_local_pilot`.
- `development-evaluation.json`: `candidate_recommended_for_manual_review: true`, `candidate_spec` со всеми полями реестра; ID равен ID прогона, XML/BIN находятся в этом прогоне. Для каждого класса нужны `per_class_holdout[class]` с precision ≥ 0.5, recall ≥ 0.25 и минимум 10 положительных изображений.
- `hard_negatives`: минимум 10 изображений и доля кадров с тревогами ≤ 0.1; для мусора минимум 5 кадров с камнями (`rocks_images`). Нужны `train_holdout_overlap: false` и явный `holdout_scope`.
- `native-parity.json`: `passed: true`, `model_sha256` должен совпадать с XML кандидата.

Эти минимальные условия допуска локального эксперимента не доказывают надёжность в поле. Отчёты должны содержать результаты настоящей проверки, а не вручную придуманные числа. После регистрации версия лишь становится доступна для отдельного явного выбора. Ранее отклонённые кандидаты мусора и дыма автоматически не импортируются и не включаются.

## Точность: текущее положение

Сорняки используют сходство с эталонами, а не вероятность. Полевые precision/recall и пропуски растений не измерены. Сходство нельзя подписывать как точность детекции.

Старый мусорный детектор отключён из-за путаницы камней/грунта с отходами. Поздние кандидаты мусора и дыма отклонены; их сохранённые отчёты показываются отдельно от принятой модели. Fire/smoke baseline экспериментальный, происхождение train и качество на воздушных кадрах не подтверждены. При отсутствии labels, отдельных splits или пригодной модели интерфейс сообщает об этом явно.

Для нового допуска нужны отдельные показатели по каждому классу, пропуски, ложные тревоги на hard negatives (особенно камнях), зафиксированный порог и holdout, не использованный для подбора. Проверки UI, synthetic training и совпадение C++/Python не являются оценкой распознавания.

## C++ и скорость

Приложение и HTTP-слой написаны на Python. Инференс экологических моделей выполняет нативный OpenVINO CPU runtime, NMS — нативный OpenCV. Для исходного weed pipeline предусмотрен C++ NMS с Python fallback (`src/vision/nms.py`). Отдельный `native/infer_openvino.cpp` — исполняемый probe для latency/parity, а не полная C++-версия приложения. Отсутствие OpenVINO не подменяется другим непроверенным детектором: направление становится недоступным.

Оптимизации маршрутов: чужие сети не компилируются и не выполняются; скомпилированные сети переиспользуются между отдельным и общим режимами. Для нескольких сетей одинакового входного размера переиспользуется подготовленный tensor в пределах одного фото. Геометрия letterbox, float32, пороги и class-aware NMS сохранены.

```bash
.venv/bin/python scripts/build_native.py
.venv/bin/python scripts/build_openvino.py
.venv/bin/python scripts/benchmark_native.py
.venv/bin/python scripts/benchmark_directions.py --baseline-ref 76f8fb2
```

Последняя команда нужна в локальной истории, где доступен исходный commit `76f8fb2`; для другой истории укажите доступный commit до изменения адаптера. Benchmark использует одинаковые реальные фото/веса, чередует замеры до/после, проверяет результаты и C++ parity. Он сохраняет новый отчёт в `outputs/directions/benchmark.json`, не меняя старые отчёты. Сборки заменяют только производные исполняемые файлы, поэтому не запускайте их одновременно с архивированием этих файлов.

Повторный замер 02.11.2026 на трёх фото: полное совпадение детекций; до 710.1/638.7/619.8 мс, после 672.4/637.6/619.5 мс. C++ на одинаковом tensor — 738.4 мс, Python API того же native runtime — 605.9 мс; max абсолютное расхождение 0. Небольшой набор и колебания CPU не доказывают общее ускорение или преимущество C++ executable над Python API. Препроцессинг-cache полезен при нескольких принятых сетях одинакового размера; сейчас такой набор моделей отсутствует.

## Проверки и разработка

```bash
.venv/bin/python -m unittest scripts.test_pilot scripts.test_pilot_http scripts.test_pilot_detector scripts.test_analysis_coverage scripts.test_directions
node --check web/pilot.js
# Дополнительно: настоящие модели и отдельная тестовая таблица БД
.venv/bin/python scripts/verify_live_directions.py
```

MariaDB-интеграция использует отдельную таблицу `photos_tests` и временные каталоги. Нужна работающая проектная БД; на production-фото эти тесты не опираются. Тесты очереди с искусственными процессами проверяют изоляцию, последовательность, отмену, ошибки и restart; не качество моделей. Browser-проверки нужно выполнять отдельно на desktop и mobile после перезапуска backend и перезагрузки страницы.

Главные компоненты: `web_pilot.py` — HTTP; `src/pilot/service.py` — очередь фото; `directions.py` — оркестрация; `workspaces.py` — данные, версии и training queue; `scripts/train_direction.py` — ограниченный offline-тренер; `src/pilot/detector.py` — OpenVINO-адаптер; `web/pilot.*` — интерфейс.

Предыдущая документация других интерфейсов и CLI сохранена в [docs/LEGACY_README_RU.md](docs/LEGACY_README_RU.md). Она описывает исторические режимы; текущий запуск пилота и ограничения определены этим README и кодом.
